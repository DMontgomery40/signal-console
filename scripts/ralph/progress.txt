  - **SQLite UNIQUE + NULL is the trap.** When you assert "INSERT duplicate row throws UNIQUE," every column in the UNIQUE tuple must be non-NULL on both rows. SQLite treats NULL as distinct from any other value (including NULL), so a UNIQUE over `(..., game_id, window_start, window_end)` does NOT fire if any of those three is NULL. My first test had two scope='game' rows with NULL window bounds — it passed silently. Fix: fill all eight UNIQUE-key columns on the collision row (mix scope + game_id + window_start + window_end), or assert the auto-index exists via `sqlite_master WHERE type='index' AND tbl_name='detector_runs' AND sql IS NULL` (the auto-index has sql=null because it's implicit).
  - **`CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS` is all you need for idempotence.** The migration runs to completion on the first call and is a no-op on subsequent calls — no version table needed at this stage. If future schema migrations land (0002-…), the runner will need a `schema_migrations` ledger; out of scope for US-005.
  - **better-sqlite3 file-resolution under tsx + ESM.** `dirname(fileURLToPath(import.meta.url))` resolves to the source dir (`packages/db/src/cache-migrations/`) under both tsx-direct execution and vitest. The 0001-init.sql sits next to runner.ts and is read at call time via `readFileSync(..., "utf8")`. This works because we never bundle/emit — `noEmit: true` + tsx run-from-source. If a future task ever introduces a build step that copies dist/, the .sql file will need to be copied alongside (e.g. tsup `loader: { ".sql": "file" }` or an explicit cp step).
  - **PRAGMA foreign_keys is OFF by default in SQLite.** The migration's `ON DELETE CASCADE` is inert unless `PRAGMA foreign_keys = ON` is set on the handle. `openCacheDb()` sets it; the cascade test sets it manually after `new Database(":memory:")`. Any future code that opens the cache DB outside `openCacheDb()` must also set this.
  - **Don't use arrow-shorthand `() => voidFn()` in vitest `expect(...).toThrow()` blocks.** The `no-confusing-void-expression` rule rejects it; wrap in braces: `expect(() => { voidFn(); }).toThrow()`. Hit this on the idempotence test (`runMigrations` returns void).

The PRD's 'desk-stable' tag (US-018, US-021, US-028, US-029, US-030) and 'internal' tag (US-017, US-019, US-020, US-034) come straight from the route schema.
  - **`schema.response` shapes pre-serialise responses.** I added per-status response schemas (`200: liveResponseSchema`, `503: readyFailResponseSchema`). Fastify uses these for fast-json-stringify, which improves response time AND publishes the response shape into openapi.json. For US-018+ when Zod schemas land, use `zod-to-json-schema` (or fastify's `withTypeProvider`) to derive these — but bare JSON Schema literals with `as const` and a `: const` flavor work today without `as`. Note: I avoided `as const` directly (eslint blocks it) by using value-typed schemas; better-sqlite3 typing of `Database.RunResult` etc. lives in the db package, so apps/api need not import it.
  - **`openGoldDb()` requires a valid SQLite file, not just any path that exists.** The route tries openGoldDb(path) inside a try/catch; if the file is missing OR the file exists but isn't a valid SQLite header, better-sqlite3 throws and the catch block emits 503 with `err.message`. To seed a real DB in tests, I added better-sqlite3 + @types/better-sqlite3 as devDeps to apps/api and call `new Database(path)` + `db.exec("CREATE TABLE IF NOT EXISTS sentinel ...")` + `db.close()` — that produces a 4 KB DB file that openGoldDb can open read-only. Future health/ready-style tests can reuse this `seedRealGoldDb()` pattern (lift to a shared test helper if a third caller appears).
  - **`db.prepare("SELECT 1").get()` then `db.close()` in a finally block.** This is the canonical readiness ping. The handler uses a single try/catch (the SELECT 1 itself shouldn't throw against a fresh DB, but a corrupt-DB / file-locked scenario could throw at prepare/get); the finally ensures the handle closes either way.
  - **`reasonFrom(err: unknown): string`** is a tiny narrow-then-string helper. Pattern: `err instanceof Error ? err.message : typeof err === 'string' ? err : 'unknown error'`. Repeatable for any future route that needs to render a caught error as a string under `consistent-type-assertions: never`.
  - **`noUncheckedIndexedAccess: true` + `consistent-type-assertions: never` + `no-unsafe-assignment` interaction is a thorny test gotcha.** When asserting on the openapi.json document body, the natural pattern of `body['paths']['/v1/...']['get']['tags']` is unworkable under these strict rules: every Record<string, unknown> lookup returns `unknown | undefined`, and `as` casts are forbidden. The pattern that DOES work (used here):
    1. `function isRecord(v: unknown): v is Record<string, unknown> { return typeof v === 'object' && v !== null; }`
    2. NARROW (don't annotate): `const pathsValue = body['paths']; if (!isRecord(pathsValue)) throw new Error(...);`
    3. If you write `const pathsValue: unknown = ...`, the explicit annotation ERASES the subsequent isRecord narrowing — TS forces it back to `unknown` for downstream uses.
    4. For closures, pass the narrowed Record explicitly as a parameter: `tagsForGet(pathsValue, "/v1/health/live")` — capturing it implicitly drops the narrowing inside the closure (TS treats nested-function captures conservatively).
    5. Inside the helper, the parameter's static type is `Record<string, unknown>` and `params[path]` returns `unknown`, which is then narrowed again via isRecord. No `as`, no `any`, no unsafe-assignment errors.
    6. Reuse this exact pattern in US-018+ when validating openapi snippets, response bodies of unknown shape from inject(), or any other "I have unknown JSON, walk into it" scenario. Eventually we'll factor it into a tiny `apps/api/tests/_helpers/walk.ts` — premature today with one caller.
  - **`@signal-console/db` exports `openGoldDb` and `GOLD_DB_PATH` from the barrel.** Import is `import { GOLD_DB_PATH, openGoldDb } from "@signal-console/db";`. Adding it to apps/api was a 1-liner in dependencies (`"@signal-console/db": "workspace:*"`) plus `pnpm install` (no other configuration needed — pnpm-workspace.yaml already includes apps/*).
  - **`app.swagger()` is the synchronous accessor** for the in-memory OpenAPI doc; it's safe to call after registration. The route handler in server.ts uses `(_request, reply) => { reply.send(app.swagger()); }` — Fastify serialises the doc. The /openapi.json handler is NOT auth-exempt (per FR-15: only /v1/health/live is exempt); test fixtures pass the token explicitly.
  - **Existing US-016 auth test had to be touched.** The original test asserted statusCode === 404 on /v1/health/live with a comment acknowledging "/v1/health/live does not exist as a route yet (US-017 owns that)". Now that we own it, the assertion flips to 200 + body { ok: true }. Future stories that land a route the auth test stubbed-out as 404 will need the same touch-up — search for "does not exist as a route yet" in apps/api/tests/ if you see this story-handoff comment elsewhere.

  - **ISO 8601 duration parsing.** A practical subset is `^P(?!$)(?:(\d+)W)?(?:(\d+)D)?(?:T(?!$)(?:(\d+)H)?(?:(\d+)M)?(?:(\d+(?:\.\d+)?)S)?)?$`. We deliberately omit Y (years) and the pre-T M (months) units because they're calendar-relative and not what /v1/games callers ever ask for. The `(?!$)` guards reject degenerate `P` and `PT` forms. Future routes that need to accept `since` (US-028 live, US-034 backtest) should import `isValidIsoDuration` and `parseIsoDuration` from `../services/games` rather than re-implementing — or extract to a shared `apps/api/src/services/_helpers/iso-duration.ts` when a third caller appears.
  - **Service layer borrows GoldDbHandle from openGoldDb's return type.** `type GoldDbHandle = ReturnType<typeof openGoldDb>;` avoids importing better-sqlite3 types directly into the service module. Same pattern as scripts/verify-queries.ts. Future services that take a DB handle (US-019 settings, US-021 board, US-028 live, US-029 microstructure) should follow this — keeps the import graph small and tied to one canonical type source.
  - **`exactOptionalPropertyTypes: true` interacts with Zod query schemas.** A Zod `.optional()` field produces `string | undefined`, but `ListGamesArgs.sport?: string` (without `| undefined`) won't accept that. Declare service args as `sport?: string | undefined` explicitly. Pattern repeats for any future service that accepts an optional field from a Zod-validated input.
  - **`Array.isArray` narrows to `any[]` in TS, breaking `no-unsafe-assignment` on member access.** When validating Fastify response bodies under strict eslint, wrap the check in a typed predicate: `function isUnknownArray(v: unknown): v is readonly unknown[] { return Array.isArray(v); }`. Then `arr[i]` is `unknown`, which `isRecord` can narrow. Pattern reusable in all future API tests that walk response shapes (US-019, US-020, US-021, US-028, US-029, US-030, US-034).
  - **Response wrapper `{ games: [...] }` vs bare array.** I chose the wrapper for /v1/games. Reason: leaves room for pagination metadata (`{ games, total, nextCursor }`) without a breaking change. UI in US-024 will `useGames()` and access `.games`. Adopt the same convention for any list endpoint added later (US-029 microstructure may want this).
  - **fast-json-stringify strips undeclared properties.** `schema.response: { 200: schemaLiteral }` is enforcing — every column the service projects MUST appear in the JSON schema, including nullable ones (`status: { type: ["string", "null"] }`). If a future column is added to the service projection but forgotten in the response schema, the response will silently drop it. To debug: temporarily remove `schema.response`, observe Fastify's raw output, then update the schema literal.
  - **Per-request DB open is fine.** openGoldDb is fast (no syscalls beyond file open + a few pragma reads) — opening a fresh handle on every request and closing it in `finally` is the simplest correctness model, matches health.ts, and avoids concurrent-handle aliasing if Fastify ever bumps concurrency. If profiling later shows this is a hotspot (Phase 3+), switch to a per-process handle decorated onto `app`, but don't over-engineer it now.
  - **Inline CTE with template strings beats CREATE TEMP VIEW.** The route never `CREATE TEMP VIEW`s — `PRAGMA query_only=ON` forbids it. Instead `WITH v_games AS (${v_games}) SELECT ... FROM v_games WHERE ...`. The CTE name is the only thing the caller references; underlying physical column names live exclusively in packages/db/src/sport-views.ts. If a future schema migration renames a column, the fix is one file.

The synchronous arrow `(request, reply) => { reply.send(...); }` works even when calling reply.send inside a try/finally with db.close — reply.send is fire-and-forget under Fastify v5, and Fastify schedules the actual flush on the next tick. Tests confirm 200/404/400 all flow correctly.
  - **OpenAPI param path uses `{gameId}`, not `:gameId`.** Fastify registers routes with `:gameId` syntax, but @fastify/swagger transcribes it to `{gameId}` for the OpenAPI doc (RFC 6570 path templates).
