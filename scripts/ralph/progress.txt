SQLite treats NULL as distinct from any other value (including NULL), so a UNIQUE over `(..., game_id, window_start, window_end)` does NOT fire if any of those three is NULL. My first test had two scope='game' rows with NULL window bounds — it passed silently. Fix: fill all eight UNIQUE-key columns on the collision row (mix scope + game_id + window_start + window_end), or assert the auto-index exists via `sqlite_master WHERE type='index' AND tbl_name='detector_runs' AND sql IS NULL` (the auto-index has sql=null because it's implicit).

If future schema migrations land (0002-…), the runner will need a `schema_migrations` ledger; out of scope for US-005.
  - **better-sqlite3 file-resolution under tsx + ESM.** `dirname(fileURLToPath(import.meta.url))` resolves to the source dir (`packages/db/src/cache-migrations/`) under both tsx-direct execution and vitest. If a future task ever introduces a build step that copies dist/, the .sql file will need to be copied alongside (e.g. tsup `loader: { ".sql": "file" }` or an explicit cp step).
  - **PRAGMA foreign_keys is OFF by default in SQLite.** The migration's `ON DELETE CASCADE` is inert unless `PRAGMA foreign_keys = ON` is set on the handle. `openCacheDb()` sets it; the cascade test sets it manually after `new Database(":memory:")`.   - **Don't use arrow-shorthand `() => voidFn()` in vitest `expect(...).toThrow()` blocks.** The `no-confusing-void-expression` rule rejects it; wrap in braces: `expect(() => { voidFn(); }).toThrow()`. Hit this on the idempotence test (`runMigrations` returns void).
