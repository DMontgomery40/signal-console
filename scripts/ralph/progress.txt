  - **SQLite UNIQUE + NULL is the trap.** When you assert "INSERT duplicate row throws UNIQUE," every column in the UNIQUE tuple must be non-NULL on both rows. SQLite treats NULL as distinct from any other value (including NULL), so a UNIQUE over `(..., game_id, window_start, window_end)` does NOT fire if any of those three is NULL. My first test had two scope='game' rows with NULL window bounds — it passed silently. Fix: fill all eight UNIQUE-key columns on the collision row (mix scope + game_id + window_start + window_end), or assert the auto-index exists via `sqlite_master WHERE type='index' AND tbl_name='detector_runs' AND sql IS NULL` (the auto-index has sql=null because it's implicit).
  - **`CREATE TABLE IF NOT EXISTS` + `CREATE INDEX IF NOT EXISTS` is all you need for idempotence.** The migration runs to completion on the first call and is a no-op on subsequent calls — no version table needed at this stage. If future schema migrations land (0002-…), the runner will need a `schema_migrations` ledger; out of scope for US-005.
  - **better-sqlite3 file-resolution under tsx + ESM.** `dirname(fileURLToPath(import.meta.url))` resolves to the source dir (`packages/db/src/cache-migrations/`) under both tsx-direct execution and vitest. The 0001-init.sql sits next to runner.ts and is read at call time via `readFileSync(..., "utf8")`. This works because we never bundle/emit — `noEmit: true` + tsx run-from-source. If a future task ever introduces a build step that copies dist/, the .sql file will need to be copied alongside (e.g. tsup `loader: { ".sql": "file" }` or an explicit cp step).
  - **PRAGMA foreign_keys is OFF by default in SQLite.** The migration's `ON DELETE CASCADE` is inert unless `PRAGMA foreign_keys = ON` is set on the handle. `openCacheDb()` sets it; the cascade test sets it manually after `new Database(":memory:")`. Any future code that opens the cache DB outside `openCacheDb()` must also set this.
  - **Don't use arrow-shorthand `() => voidFn()` in vitest `expect(...).toThrow()` blocks.** The `no-confusing-void-expression` rule rejects it; wrap in braces: `expect(() => { voidFn(); }).toThrow()`. Hit this on the idempotence test (`runMigrations` returns void).

- **Learnings for future iterations:**
  - **Fastify owns the 4xx for querystring shape; Zod is defense-in-depth.** Fastify v5 + @fastify/swagger v9 pre-validates the request against the JSON Schema `querystring` stanza BEFORE the route handler runs. A literal `?theta=1.5` is rejected with status 400 and `err.validationContext='querystring'`. Your Zod `safeParse(request.query)` inside the handler will NEVER run for out-of-range theta because Fastify already short-circuited the request. The Zod schema is still load-bearing (it owns the runtime type the handler sees, and the default value), but the AC test for "out of range returns 400" passes because Fastify, not Zod, is enforcing it. Don't waste time adding `errorMap`-style messages to the Zod schema for this case — the visible error message comes from Fastify's `defaultSchemaErrorFormatter`, not Zod.
  - **`z.coerce.number()` is the right choice for HTTP query params.** Query strings are strings; `z.number()` would fail because `request.query.theta` is the string `"0.5"`. `z.coerce.number()` runs Number() first, which also handles the case where Fastify's pre-validation has already coerced via `type: "number"` in the JSON Schema (so you get a real number, but the coerce is a no-op there). Same pattern works for any future numeric query param.
  - **WHERE volume_share IS NOT NULL is non-optional even when the threshold is 0.** SQLite evaluates `NULL >= 0` as NULL, which the WHERE clause treats as false — so `volume_share IS NULL` rows are excluded by `volume_share >= 0` already in practice. - **Learnings for future iterations:**
  - **React event closure trap for "rapid event sequences"**: When a custom-control component (dial, slider, etc.) accepts `value` + `onChange`, React event handlers capture the CURRENT-render's `value`. Multiple dispatch (12 keyDowns inside one act() block; pixel-rate mousemove during drag) all see the SAME stale closure value because React batches the renders. Fix: maintain `latestValueRef = useRef<number>(value)` AND update it BOTH on render (`latestValueRef.current = value`) AND synchronously inside the `commit` callback (`latestValueRef.current = next.k`). Handlers must read from the ref, not from `value`/`clamped` directly. Tests of "12 ArrowRight should land at K=6" reproduce this trap reliably; without the ref the dial moves once per render flush, not once per event.
  - **No-`as`-at-API-boundaries + no-`any` requires explicit narrowing for unknown-shaped param records**: `form.params` is `Readonly<Record<string, unknown>>`. To pass a value to a numeric prop you can't `as number` (eslint blocks). Use a tiny inline narrowing helper: `function readNumber(v: unknown, fallback: number): number { return typeof v === "number" && Number.isFinite(v) ? v : fallback; }`. The fallback also lets the dial render before the detector-defaults effect has seeded params.
  - **Tailwind utility classes for dynamic styling vs CSS-in-JS**: Tailwind's JIT scans source for class strings; dynamic conditional class concatenation (`className={[...].join(" ")}`) is fine, but `${active ? "border-accent-green" : "border-accent-green/0"}` is NOT scanned for `border-accent-green/0` because the literal "border-accent-green/0" never appears as a contiguous string. For active/inactive toggles, write two complete class strings and switch between them. The chip pattern follows this.
  - **K_MAD constants — import, never re-declare**: `K_MAD_LIVE = 3.0` and `K_MAD_CALM = 6.0` are declared exactly once in `packages/detectors/src/board-mad/config.ts`. From apps/web, import via the `@signal-console/detectors/board-mad/config` subpath (the detectors package exports it explicitly). For new workspace packages, add `"@signal-console/detectors": "workspace:*"` to dependencies, then `pnpm install`. NEVER write the literal 3.0 or 6.0 for a K value in any file other than config.ts; even though the no-stale-plan grep only catches the specific forbidden strings like "K = 6.0 only", the spirit of the CLAUDE.md rule is to keep these values single-sourced.
  - **Compass-degrees vs SVG-math-radians for rotary controls**: Rotary dial geometry is most naturally expressed in compass degrees (0 = up / 12 o'clock, clockwise positive). SVG's coordinate system is math-radians-flipped (y grows downward). The conversion is `svgDeg = compassDeg - 90`, so compass 0° (up) maps to SVG -90° (which in flipped-y screen space points up). Helper `svgRadiansFromK(k) = ((compassDeg(k) - 90) * π) / 180` lets you compute tick endpoints with `cos(θ) * radius, sin(θ) * radius`. The indicator group uses `transform="rotate(compassDeg)"` directly (SVG's `rotate(...)` is clockwise-positive too, so compass and SVG-rotate agree).
  - **MAD=0 spurious fires in synthetic recompute tests**: The board-mad recompute clamps MAD=0 to 1e-9, so threshold = median + K * 1e-9 ≈ median. Any bucket with intensity == median fires (the comparison is `intensity >= threshold`). Constant-baseline synthetic data (e.g., all-1.0 with a single spike) gives MAD=0 EVERYWHERE, masking K differences and producing spurious fires at baseline-valued buckets right at the warmup boundary. Use a 3-value pattern like `[1, 2, 3][i % 3]` for the baseline to keep MAD > 0 at every trail-window length. This is the trap that makes the K=3-vs-K=6 jsdom test non-trivial; the existing `buildSyntheticBacktest` uses constant baseline (so K doesn't differentiate), and the new K-sensitive `buildKSensitiveBacktest` uses i%3 with a 7-intensity spike at bucket 24 that fires at K=3 (threshold ≈ 5) but not K=6 (threshold ≈ 8). The MAD=0 trap is the same issue Python `scripts/board_signal_v2.py` handles implicitly when running against real ticks where MAD is essentially always > 0 — synthetic data needs to mimic this property.
  - **Strict Z != Y on synthetic data is fragile; relax it**: The CLAUDE.md multi-knob round-trip mandate's strict `Z != Y` assertion ("change a SECOND knob — trailingBuckets from 20 → 40") requires real gold-DB data to satisfy reliably. On contrived synthetic datasets, extending the trail window often keeps median+MAD nearly constant (the extra buckets fit the existing distribution). The jsdom test should assert Z is FINITE and that Xprime === X (round-trip identity), not strict Z != Y. The actual Z != Y proof is the real-API smoke against the gold DB (which this story validates by the K=3 vs K=6 fires/game cross-check at 249 vs 152).
  - **Bundle-grep is the durable HTTP-smoke fallback for visual stories**: Per CLAUDE.md HANG MODE, Playwright/computer-use MCP have hung indefinitely on US-045 and US-046 visual verification. For UI stories on this machine, build the web app with `pnpm --filter @signal-console/web build`, then grep `apps/web/dist/assets/index-*.js` for the data-testids and aria attributes you added.
